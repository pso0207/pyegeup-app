# 07. Expo 프론트와 API 연결

## 이번 단계의 결과

프론트의 목업 사건 조회 하나를 실제 Spring Boot API로 교체합니다. 모든 목업을 한꺼번에 없애지 않습니다. 서버 구현과 화면 문제가 섞이지 않도록 조회 한 건부터 연결합니다.

## 연결 전 계약표

코드보다 먼저 프론트가 기대하는 값과 서버 응답을 비교합니다.

| 의미 | 프론트 이름 | 서버 이름 | 형식 | 변환 필요 |
|---|---|---|---|---|
| 사건 ID | `id` | `id` | number/string | 확인 |
| 제목 | `title` | `title` | string | 없음 |
| 유죄율 | `guiltyRate` | `guiltyRate` | 0~1 또는 0~100 | 반드시 합의 |
| 마감 시간 | `closesInMin` | `closesAt` | 분/ISO 날짜 | 있음 |

이 표를 실제 응답 필드 전체로 확장합니다. 특히 비율, 날짜, enum, nullable 필드는 눈으로 추측하지 않습니다.

## 구현 순서

1. 서버를 실행하고 `curl`로 응답을 저장하지 말고 화면에서 확인합니다.
2. 프론트의 API 기본 URL을 환경 설정으로 분리합니다.
3. 공통 `fetch` 함수에서 JSON과 오류 응답을 처리합니다.
4. 사건 상세 화면 하나만 실제 API로 바꿉니다.
5. 로딩, 빈 상태, 서버 오류, 재시도를 확인합니다.
6. 같은 ID의 목업과 실제 응답을 비교합니다.
7. 연결이 안정되면 목록 조회로 확장합니다.
8. 쓰기 요청은 마지막에 연결합니다.

## 로컬 주소에서 자주 막히는 이유

- 웹 브라우저: 보통 `http://localhost:8080`
- Android 에뮬레이터: 호스트 컴퓨터를 `localhost`로 부르면 에뮬레이터 자신을 가리킵니다. 환경에 맞는 호스트 주소가 필요합니다.
- 실제 휴대폰: 컴퓨터와 같은 네트워크에 있고 컴퓨터의 로컬 IP와 방화벽 설정을 확인해야 합니다.
- 브라우저: 프론트와 API의 출처가 다르면 CORS 설정이 필요합니다.

주소를 코드 여러 곳에 박아 넣지 말고 개발·테스트·운영 환경별 값으로 분리합니다.

## AI에게 요청할 범위

```text
사건 상세 화면 하나만 목업에서 실제 API로 교체해줘.
먼저 프론트가 기대하는 필드와 서버 응답 필드를 표로 비교해줘.
로딩, 404, 네트워크 오류, 재시도 UI를 포함하고 다른 화면의 목업은 유지해줘.
웹 빌드와 가능한 테스트를 실행한 뒤 REVIEW-LOG에 기록해줘.
```

## 리뷰 질문

1. API 주소를 화면 파일에 직접 쓰지 않는 이유는 무엇인가?
2. HTTP 404와 인터넷 연결 실패는 화면에서 어떻게 다르게 처리해야 하는가?
3. 서버의 날짜 문자열은 어느 층에서 화면용 값으로 변환하는가?
4. 응답 필드가 바뀌었을 때 조용히 잘못 표시되는 문제를 어떻게 발견할 수 있는가?
5. 쓰기 요청을 재시도할 때 중복 저장 위험은 어떻게 막는가?

## 직접 재작성 과제

AI가 연결한 상세 조회를 참고하여 사건 목록 조회 함수와 로딩 상태를 직접 작성합니다. 기존 목업을 바로 삭제하지 말고 비교가 끝난 뒤 제거합니다.
