# 00. AI와 공부하는 작업 방식

## 목표

AI가 반복 코드를 빠르게 만들게 하면서도, 프로젝트를 혼자 설명하고 고칠 수 있는 상태를 만드는 것이 목표입니다.

## 매 회차 60분 루틴

### 0~10분: 문제를 먼저 적기

코드를 보기 전에 아래 네 줄을 직접 적습니다.

```text
사용자는 무엇을 요청하는가?
서버는 무엇을 검증해야 하는가?
DB에서 무엇을 읽거나 바꾸는가?
성공과 실패 응답은 무엇인가?
```

### 10~25분: 내가 먼저 시도하기

완성하지 못해도 좋습니다. 메서드 이름, DTO 필드, 테스트 이름 중 하나를 먼저 작성합니다. 15분 이상 막히면 `힌트만`으로 AI에게 요청합니다.

### 25~40분: AI 구현 비교하기

AI에게 기능 하나만 구현하게 합니다. 변경된 파일마다 다음을 확인합니다.

- 이 파일이 없으면 어떤 책임이 사라지는가?
- 입력이 어디에서 도메인 객체로 바뀌는가?
- DB 변경이 실패하면 모두 되돌아가는가?
- 사용자가 같은 요청을 두 번 보내면 어떻게 되는가?

### 40~50분: 테스트하고 일부러 깨뜨리기

정상 입력만 확인하지 않습니다. ID가 없거나, 값이 비었거나, 같은 판결을 두 번 보내는 상황을 테스트합니다.

### 50~60분: 닫고 다시 쓰기

코드를 가리고 핵심 메서드나 흐름을 다시 작성합니다. 완전히 같을 필요는 없습니다. 마지막에 `REVIEW-LOG.md`에 세 줄을 남깁니다.

```text
오늘 이해한 것:
아직 설명 못 하는 것:
다음에 직접 바꿀 것:
```

## AI 사용 비율

| 작업 | AI | 나 |
|---|---:|---:|
| 프로젝트 설정·반복 코드 | 80% | 20% |
| 단순 CRUD | 50% | 50% |
| 핵심 판결·점수 규칙 | 30% | 70% |
| 테스트 시나리오 생각하기 | 30% | 70% |
| 코드 설명과 회고 | 10% | 90% |

## 막혔을 때 규칙

1. 오류 메시지를 끝까지 읽습니다.
2. 마지막으로 정상 동작한 지점을 찾습니다.
3. 한 번에 변수 하나만 바꿉니다.
4. 20분 이상 같은 자리에서 막히면 오류 전문과 시도한 내용을 AI에게 줍니다.
5. AI가 준 수정은 바로 붙이지 말고 원인을 한 문장으로 말한 뒤 적용합니다.

## 피해야 할 패턴

- “백엔드 전부 만들어줘”처럼 범위가 큰 요청
- 실행하지 않은 코드를 쌓아두기
- 테스트 실패를 지우거나 무시하기
- 모르는 어노테이션을 그대로 복사하기
- Entity를 그대로 JSON 응답으로 보내기
- AI 설명을 이해했다는 이유로 직접 다시 쓰는 과정을 생략하기
