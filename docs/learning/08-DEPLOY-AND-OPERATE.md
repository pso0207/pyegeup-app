# 08. 배포와 운영 준비

## 이번 단계의 결과

개발 PC가 아닌 환경에서 Spring Boot와 MySQL이 실행되고, 프론트가 HTTPS API를 호출합니다. 처음부터 복잡한 자동화를 만들기보다 수동 배포 과정을 한 번 이해한 뒤 자동화합니다.

## 환경을 분리하는 이유

| 환경 | 목적 | 데이터 | 로그 수준 |
|---|---|---|---|
| local | 개인 개발 | 지워도 되는 샘플 | 자세함 |
| test | 자동 테스트 | 매번 격리 | 실패 분석 중심 |
| production | 실제 사용자 | 보존·백업 필요 | 민감정보 제외 |

DB 비밀번호, 토큰 서명 키, 외부 서비스 키는 Git에 커밋하지 않습니다. 환경 변수의 **이름과 필요한 이유**는 문서화하되 실제 값은 저장소 밖에서 관리합니다.

## 배포 전 체크리스트

- [ ] 운영 프로필에서 `ddl-auto`가 스키마를 임의 변경하지 않는다.
- [ ] Flyway 마이그레이션이 빈 운영 DB에서 순서대로 성공한다.
- [ ] 비밀값이 Git 기록과 로그에 없다.
- [ ] CORS가 필요한 프론트 주소만 허용한다.
- [ ] HTTPS를 사용한다.
- [ ] health check가 DB 장애와 서버 생존을 구분한다.
- [ ] 예외 응답에 스택 트레이스와 SQL이 노출되지 않는다.
- [ ] 백업 방법과 복구 순서를 적어두었다.
- [ ] 애플리케이션과 DB 시간대를 확인했다.
- [ ] 최소 한 번은 새 환경에서 처음부터 배포했다.

## 첫 배포 순서

1. 로컬 테스트를 모두 실행합니다.
2. 운영용 JAR을 빌드합니다.
3. 운영 환경 변수 목록을 확인합니다.
4. 빈 DB에 Flyway를 적용합니다.
5. 서버를 시작하고 health endpoint를 확인합니다.
6. 읽기 API를 확인합니다.
7. 테스트 계정으로 쓰기 API를 한 번 확인합니다.
8. 프론트 API 주소를 운영 URL로 설정합니다.
9. 서버 오류율과 로그를 관찰합니다.
10. 실패했을 때 이전 버전으로 돌아가는 절차를 확인합니다.

```text
비밀값은 출력하거나 저장소에 쓰지 마.
```

## 리뷰 질문

1. 개발 DB와 운영 DB를 같은 설정으로 쓰면 어떤 사고가 생길 수 있는가?
2. Flyway 실패 후 애플리케이션을 억지로 시작하면 왜 위험한가?
3. health endpoint가 200이어도 서비스가 고장일 수 있는 경우는 무엇인가?
4. 로그에 절대 남으면 안 되는 데이터는 무엇인가?
5. 배포 성공과 사용자 기능 정상 동작은 왜 다른 확인인가?

## 직접 작성 과제

운영 환경 변수의 이름, 용도, 값을 발급하는 곳, 교체 주기를 표로 작성합니다. 실제 비밀값은 적지 않습니다. 이어서 장애 시 확인 순서를 다섯 단계로 적습니다.
