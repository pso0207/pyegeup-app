# 06. 테스트와 리팩터링

## 목표

테스트는 점수를 받기 위한 코드가 아니라 **바꿔도 되는 범위**를 알려주는 안전망입니다. 리팩터링은 외부 동작을 유지하면서 내부 구조를 개선하는 작업입니다.

## 테스트 피라미드

| 종류 | 빠르기 | 확인하는 것 | 예시 |
|---|---|---|---|
| 단위 테스트 | 빠름 | 한 규칙과 계산 | 형량 범위, 점수 계산 |
| 슬라이스 테스트 | 중간 | 특정 Spring 계층 | Controller JSON·상태 코드 |
| 통합 테스트 | 느림 | Spring과 실제 DB 연결 | 트랜잭션, 제약, 쿼리 |
| E2E | 가장 느림 | 사용자 흐름 전체 | 로그인 후 판결 제출 |

모든 기능을 E2E로만 검사하지 않습니다. 중요한 규칙은 빠른 단위 테스트로 많이 확인하고, 계층 연결과 실제 MySQL 차이는 소수의 통합 테스트로 확인합니다.

## 리팩터링 순서

1. 현재 테스트가 통과하는지 확인합니다.
2. 바꾸려는 냄새를 한 가지 고릅니다.
3. 동작을 보존하는 작은 변경을 합니다.
4. 테스트를 다시 실행합니다.
5. 커밋합니다.
6. 성능 최적화라면 변경 전후 수치를 측정합니다.

## 초보자가 찾기 좋은 코드 냄새

- 한 메서드가 검증·조회·저장·응답 변환을 모두 수행함
- 같은 조건문이나 DTO 변환이 여러 곳에 반복됨
- 메서드 이름이 `process`, `handle`, `doIt`처럼 의도를 말하지 않음
- boolean 매개변수가 여러 개라 호출 의미를 알기 어려움
- Controller가 Entity나 Repository를 직접 다룸
- 모든 예외를 `Exception` 하나로 처리함
- 테스트가 구현 내부 메서드 호출 횟수만 확인함

## AI 리뷰 요청문

```text
코드를 수정하지 말고 리뷰만 해줘.
1) 데이터·권한·트랜잭션 버그, 2) 요구사항 위반, 3) 테스트 누락,
4) 책임과 이름, 5) 성능 순으로 봐줘.
각 문제에 재현 조건과 최소 수정 방향을 써줘. 취향 차이는 별도로 구분해줘.
```

## AI 리팩터링 요청문

```text
현재 테스트가 보장하는 외부 동작을 유지하면서 한 가지 냄새만 리팩터링해줘.
변경 전 문제, 변경 범위, 테스트 결과를 설명해줘.
새 프레임워크나 추상화는 추가하지 마.
```

## 최종 설명 시험

다음 내용을 저장소를 보지 않고 5분 안에 설명해 봅니다.

- 판결 요청 한 건이 DB에 저장되는 전체 흐름
- 중복 판결을 애플리케이션과 DB 양쪽에서 막는 이유
- DTO와 Entity를 분리한 이유
- 트랜잭션이 필요한 구간
- 테스트가 현재 보장하지 못하는 것
