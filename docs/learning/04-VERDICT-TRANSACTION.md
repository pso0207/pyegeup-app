# 04. 판결 저장과 트랜잭션

## 이번 단계의 결과

사용자가 사건에 유죄·무죄와 형량, 의견을 제출합니다. 중복 제출과 잘못된 형량을 서버가 거부합니다. 전체 구현 예시는 [백엔드 튜토리얼 12장](../BACKEND-TUTORIAL.md#12-판결-저장-api-만들기)을 참고합니다.

## 먼저 규칙을 문장으로 쓰기

- 한 사용자는 한 사건에 한 번만 판결할 수 있다.
- 무죄에는 형량이 없어야 한다.
- 유죄 형량은 정의된 범위 안이어야 한다.
- 마감된 사건에는 판결할 수 없다.
- 판결 저장과 관련 점수·티켓 변경은 함께 성공하거나 함께 실패해야 한다.
- DB의 유니크 제약으로도 중복을 막는다.

## 왜 어려운 기능인가

화면에서 버튼을 비활성화하는 것만으로 중복 요청을 막을 수 없습니다. 사용자가 두 번 누르거나 네트워크가 재시도하거나 요청 두 개가 동시에 도착할 수 있습니다. 따라서 Service 검사와 DB 제약이 모두 필요합니다.

## 구현 순서

1. Request DTO의 형식 검증 테스트
2. 판결 가능한 사건인지 확인
3. 중복 판결 확인
4. 유죄·무죄와 형량의 조합 검증
5. 판결 저장
6. 트랜잭션 경계 지정
7. DB 유니크 제약 충돌을 공통 오류로 변환
8. 통합 테스트에서 같은 요청을 두 번 전송

## AI에게 요청할 범위

```text
POST /api/v1/cases/{caseId}/verdicts 하나만 구현해줘.
먼저 도메인 규칙과 트랜잭션 범위를 설명해줘.
정상, 잘못된 형량, 마감 사건, 중복 판결 테스트를 포함해줘.
동시 요청은 DB 유니크 제약으로도 막고 예외 응답을 통일해줘.
점수 정산은 아직 구현하지 마.
```

## 리뷰 질문

1. `@Valid`가 잡는 오류와 Service가 잡는 오류는 어떻게 다른가?
2. 중복 확인 쿼리만으로 동시 요청을 완전히 막을 수 없는 이유는 무엇인가?
3. `@Transactional`이 Controller가 아니라 Service에 있는 이유는 무엇인가?
4. 저장 중 예외가 발생하면 어떤 변경이 롤백되는가?
5. 같은 요청을 재시도해도 결과가 안전하도록 만들려면 무엇이 필요한가?

## 직접 재작성 과제

AI가 작성한 중복 판결 테스트를 보지 않고 다시 작성합니다. 테스트 이름에 조건과 기대 결과가 드러나게 합니다.
